# AstronHub 内网插件管理实施规格

状态：产品范围已确认，正在实施，尚未全部完成。确认日期：2026-10-14；进度更新：2026-10-15。

跟踪器：沿用仓库本地 Markdown 约定。决策索引为 [Wayfinder](../.scratch/plugin-update/map.md)，实施任务及阻塞关系见 [实施索引](../.scratch/plugin-update/implementation.md)。实现统一进入 `codex/plugin-update-integration`，不得将规划完成标记为功能完成。

本规格记录插件管理访谈 Q1–Q28 的确认结果，并将其拆分为可交付任务。它承接 [能力平台设计](25-astronhub-capability-platform-design.md)，新增服务器向内网 Git 和 npm 发布的渠道；不将应用软件自动更新纳入插件生命周期。实施前基线只有插件模型和只读目录；当前进展以实施票证据为准，不能将本规格中的全部行为视为已实现。Claude/Codex/Pi 离线 ZIP/TGZ、仓库预览、审核及受限托管发布的操作与限制见 [管理指南](skillhub/guide/plugin-management.md)。

已合入独立实施票 01–05：插件草稿和审核、受限托管发布、三宿主离线单包及仓库导入、下载与组件治理、内网 npm 发布和独立依赖上传、Git 原生市场。发布恢复仍按任务图推进。本地实际发布组件已分别供 Pi、Claude Code、Codex 完成隔离安装，Claude/Codex 的新版本更新与旧 commit 保留也已验证；这些证据不代替真实企业 Git/npm、复杂插件运行及最终集成验收。

## 1. 产品边界

- 星枢管理插件上传、版本、检查、审核、发布、下载及安装指引。
- 首版支持 Claude Code、Codex、Pi 三个宿主；插件版本可只提供其中一个宿主的发行物。
- 用户通过宿主原生机制安装、启用、更新或移除。星枢不管理终端设备，也不在用户电脑上远程执行安装。
- 部署处于内网。公开插件由人工下载后导入；服务器不得自动访问公开市场、npm 或其他公网依赖源。
- 管理员在后台配置内网 npm 来源和 Git 发布目标。服务器直接发布包和维护市场，用户不需要再次手动上传 npm 或编辑市场仓库。
- 独立 MCP 目录的提交、审核或网关能力不在本次插件管理范围；插件自带 MCP 配置作为包内资源解析。

## 2. 身份、权限和可见性

沿用 `plugin:@namespace/slug`、现有用户和命名空间体系。

| 操作 | 权限 |
| --- | --- |
| 提交单插件、提交新版本 | 具有该命名空间提交权限的成员 |
| 维护命名空间插件 | 命名空间 OWNER/ADMIN，以及有权维护本人插件的提交者 |
| 批量导入仓库压缩包 | 目标命名空间 OWNER/ADMIN、平台 PLUGIN_ADMIN、SUPER_ADMIN |
| 审核 | 平台 PLUGIN_ADMIN、SUPER_ADMIN |
| 直接发布 | SUPER_ADMIN，仍须通过结构检查并记录审计 |
| 依赖 TGZ 上传和确认 | PLUGIN_ADMIN、SUPER_ADMIN |

批量导入每次选择一个目标命名空间。首版 Git 仓库统一按 public 配置处理；团队市场拆分用于分类和名称隔离，不形成访问控制。

- 只有 PUBLIC 插件发行物进入原生 Git/npm 分发渠道。
- NAMESPACE_ONLY、PRIVATE 插件保留星枢鉴权下载和本地安装指引，不把受限内容写入 public Git 或公开的 npm 插件来源。
- 已进入 public 渠道的内容不能靠改变星枢可见性收回。变更可见性和下架时须展示已有外部分发记录；已有副本的撤回属于单独的渠道治理操作。

## 3. 包、版本和组件

保留 `PluginProject -> PluginRelease -> PluginDistribution` 模型。每个发行物归属于一个宿主，并记录原生名称、原生版本、包摘要、宿主要求、资源清单、来源和安装指引。

以插件版本为审核和发布单位；一个版本可以包含一个或多个宿主发行物。发布内容固定：替换包或补入新宿主都创建新版本。目录展示名称、介绍和分类可以编辑，包内清单、代码、配置不得由星枢静默改写。内网改造须重新打包，并记录原始来源和版本说明。

Skill、MCP、Agent、Hook、LSP、Extension、Prompt、Theme 等包内资源只构成组件清单。不因发现资源自动创建独立 Skill/MCP 条目。显式关联是非所有权关联；关联对象保持独立权限、版本和生命周期，不能借关联泄漏受限内容。

## 4. 离线导入

接受单插件 ZIP、Pi npm TGZ，以及包含多个插件的仓库压缩包。仓库 ZIP/TGZ 逐目录识别候选原生包；宿主适配器明确处理清单、约定目录及支持的格式版本。插件不必包含根目录 SKILL.md。

流程：上传归档 -> 有预算的解压和扫描 -> 展示候选 -> 选择项目或创建新项目 -> 分别创建草稿 -> 提交审核。记录目录路径、宿主、原生名称、版本、资源清单、检查证据和失败原因。

预览结果分为新插件、新版本、相同内容、内容冲突、无法识别。相同内容可以跳过；相同目标版本但不同内容禁止覆盖。无法识别的目录不入库。候选失败不阻断其他候选；顶层归档安全检查或解压预算失败终止该次扫描。

| 默认限制 | 值 |
| --- | --- |
| 单插件包或单依赖包 | 100 MiB |
| 仓库压缩包 | 500 MiB |
| 单次解压总量 | 2 GiB |
| 文件数量 | 20,000 |
| 候选插件数量 | 100 |

以上参数可由后台调整。原始文件使用插件专用存储前缀；不得套用 Skill 的包政策或复用 Skill 对象路径。检查归档路径、链接、重复文件和展开预算，不执行导入文件或 npm lifecycle scripts。

## 5. 检查和审核证据

分别记录静态检查、人工审核、运行测试；没有运行证据时标记为未验证。

- 静态检查包括清单类型、资源引用、路径包含关系、包身份、依赖声明、摘要及宿主格式要求。
- 审核者可以查看文件和检查结果，填写测试结论及测试环境。
- 格式正确不等于安全扫描通过，也不等于宿主运行测试通过。
- 插件依赖可能包括 npm 包、Node/Python、程序和 MCP 服务。详情页展示安装前提；不能仅凭上传成功宣称完整离线可安装。
- npm 依赖使用内网源。缺失依赖明确列出，不回退公网；依赖可用性和安装环境要求分开记录。

## 6. npm 发布渠道

内网 npm 库存放 Pi 插件及第三方依赖。后台维护默认源和其他允许的内网源，发行物选择配置的源。服务器发布凭据与普通用户安装认证分离；不得写入包、安装指引、审计正文或日志。

审核通过后启动插件版本发布。npm 渠道保留原始包名和原生版本，固定版本发布；已有相同包名和版本时核对内容，相同内容复用，不同内容阻止发布。不得为了避开冲突自动改名。

第三方依赖提供独立上传入口：管理员上传一个或多个 TGZ，检查包名、版本、文件结构和摘要，确认后由服务器发布。记录上传者、来源、包摘要、目标库、结果和重试情况；不创建插件项目，不进入插件目录，不套用插件审核流程。

Pi 安装指引使用固定包版本，并提供内网 registry 配置方法。普通用户认证通过其 npm 配置处理，不自动改写全局默认源。源配置变化不改写历史发布记录。

## 7. Git 原生市场

管理员配置内网 Git 目标和发布凭据。星枢自动生成索引、同步 Claude Code/Codex 原生文件并提交推送。管理员预建目标仓库即可；产品不要求公网 Git，也不依赖某一厂商的仓库创建 API。

| 命名空间 | 原生市场名称 |
| --- | --- |
| global | astronhub |
| 其他命名空间 | astronhub-{namespace_slug} |

每个命名空间市场分别生成 Claude Code 的 `.claude-plugin/marketplace.json` 和 Codex 的 `.agents/plugins/marketplace.json`。索引使用各宿主格式，不假设两种 JSON 完全相同。发布任务记录目标仓库、索引、发行物摘要和 Git commit。

市场名称隔离不同命名空间的插件身份。原生名称仍须满足宿主规则，同一市场内的名称冲突须在发布前阻止。Pi TGZ 和第三方依赖进入 npm 库，不重复复制到 Git 市场。

Git 保留可追踪的发布历史。历史版本安装指引使用不可变 commit、tag 或星枢包；当前市场索引展示选定的已发布版本。原生安装/刷新命令按支持的宿主版本生成，不虚构所有宿主都具有相同 CLI 能力。

## 8. 发布执行和治理

审批结论与渠道执行结果分开持久化。业务版本仍以发布完成为可见边界；渠道执行状态不等同于业务发布状态。

1. 固定已批准的发行物和配置快照，创建发布任务。
2. 根据实际发行物和可见性计算所需渠道；受限版本仅使用鉴权下载渠道。
3. 分渠道上传/同步并记录成功结果。
4. 所需渠道全部成功后，把星枢版本标记为已发布并维护项目当前版本。
5. 失败保留已成功结果，重试失败渠道。客户端可能已能从成功的 Git/npm 渠道取得审核通过的内容；界面展示发布未完成，不宣称跨系统原子发布。

后台执行应具有持久任务、幂等标识、并发互斥、恢复和审计。对 npm 的已存在包和 Git 推送的不确定结果先核对，不能直接覆盖或盲目重复执行。

每个 HOSTED/npm/Git 渠道采用短事务领取、独立心跳续租、事务外完整性校验或网络请求、令牌与计划修订共同校验的结果提交。保留每次执行的起止时间、租约、结果、错误和迟到回执，提供分页历史。过期执行须先核对原始目标；读失败或仍不确定时保持 `UNKNOWN`。确认不存在的结果只允许下一次原计划重试或显式修订，本次核对不进行写入。

管理员可对已批准但未完成发布的必要外部渠道进行显式恢复：仅 `BLOCKED` 和确定失败的 `FAILED` 可选择目标修订、填写原因、预览和确认。最初快照与每次修订均保留；成功、运行中及 `UNKNOWN` 不允许改投。恢复不改变所需渠道、包内容、审批结论或审批任务顺序，也不新增永久取消状态。隐藏和归档可立即用于目录管控，未完成任务仍阻止改变可见范围。

普通下架不自动删除 npm 包。管理员可单独执行渠道撤回/禁用，记录支持情况和结果。不能承诺删除已经克隆的 Git 历史或用户已下载的副本。归档、隐藏、版本下架保持项目与发行物的独立语义。

显式渠道治理单独保留操作、原因、原始目标及回执，不覆盖发布成功记录。npm 远程删除返回 `UNSUPPORTED` 并明确包仍保留，本地安装源禁用单独展示。Git 撤回仅删除原目标当前索引，保留版本文件与 Git 历史；墓碑按原审批顺序阻止旧任务重放，新批准仍可更新市场。撤回和发布任务进入同一个公平轮询队列，复用 Git 传输和意图证据，未知撤回结果也先在原目标只读核对。

## 9. 实施任务和验收

| 顺序 | 任务 | 主要验收 |
| --- | --- | --- |
| P1 | 插件写模型、权限、审计、版本不可变及审批记录 | 命名空间权限；越权拒绝；审批结果与渠道状态分离；已发布内容不可替换 |
| P2 | ZIP/TGZ 上传、预算解压、批量扫描和选择导入 | 三种导入；路径/链接拒绝；超限；相同内容跳过；单项失败继续 |
| P3 | Claude Code、Codex、Pi 静态适配器、资源清单和指引 | 代表性原生样例；格式版本；资源路径；原生名称；运行证据不被静态结果替代 |
| P4 | 插件审核及目录详情、版本页、管理页 | 单插件和批量流程；文件查看；宿主发行物展示；组件显式关联和权限 |
| P5 | npm 源配置、插件发布、独立依赖上传 | 真实内网 registry；固定版本；内容冲突；认证隔离；失败和重试；无公网请求 |
| P6 | Git 目标配置和两种市场生成 | 真实内网 Git；按命名空间市场；原生宿主注册、安装及更新；仅 PUBLIC 内容输出 |
| P7 | 发布任务恢复、下架及渠道治理 | npm 成功/Git 失败；不确定推送恢复；只重试失败渠道；不自动删除成功包 |
| P8 | 集成验证、OpenAPI 生成、运维文档 | 三宿主完整链路；内网依赖；旧版本获取；限制配置；必需的后端/前端/staging 检查 |

后端遵循现有模块边界：规则和仓库端口在 domain，基础设施发布实现放在外层，app 服务编排，复杂详情和管理列表交给 app query repository。前端按 Feature-Sliced Design 建立插件管理功能。不得手动编辑生成的 OpenAPI 类型。

## 10. 与应用自动更新的关系

应用安装包和更新源属于软件中心，不属于插件市场。其扩展已单独确认，按 [软件发布和更新渠道规格](28-software-release-update-channels.md) 并行实施。优先兼容现有 GitLab tags/raw 读取协议，并按应用显式开启匿名更新源。两项业务共享平台基础设施，保持独立权限和生命周期；研究结论与已确认规格均不代表功能已实现。

## 11. 实施依赖与测试边界

P1–P8 是范围和验收分组，不是逐层施工顺序。实际任务按可验证的完整用户流程拆分，包含数据约束、权限、API、界面及测试，并以本地实施票的阻塞关系选择可开始的工作。应用更新 U1–U7 使用独立任务链，最后汇合集成验收。

拟在领域服务、HTTP 接口、原生解析器和 Git/npm 渠道适配器、页面操作四类公开边界验证行为。原生客户端安装与实际内网渠道验收单独记录；缺少真实环境或样本时保留未验收项，不以单元测试替代。
